# Production CRM: Google sign-in and shared database

## Intent and agreed access policy
Make the existing CRM usable at https://everydaystravel.co.uk/crm from multiple devices. Retain the monochrome shadcn interface, pipeline, shared inbox, follow-ups and vehicle calendar. The user explicitly chose immediate shared access for **any Google account** after being asked whether accounts need staff approval or anyone signed in should see shared customer records, inbox and bookings. Do not silently replace that choice with a company-domain restriction or invitation gate. Google identity must still be verified by the server. There is one shared company workspace, not an isolated workspace per user. This means anyone with a verified Google account can view and edit its records and use the shared inbox's explicit reviewed send action.

## Implementation decisions (builder choices)
- Follow the existing approved Firebase architecture: Firebase Authentication for Google sign-in, Firestore in europe-west2 (London), server-only database access with firebase-admin. Deny all direct Firestore client access.
- Use a short-lived Firebase ID token only to establish a server session. HttpOnly, Secure production, SameSite=Lax session cookie; verify expiry, revocation and verified Google-provider identity on every CRM page/API request. No anonymous or password access, no browser token persisted beyond sign-in.
- Require recent Google authentication for session creation. Validate same-origin mutations and CSRF on login/logout. Use a configured canonical CRM origin in production, never derive OAuth targets from an untrusted Host header. Production fails closed when required configuration is absent.
- Existing development local mode remains explicit and localhost-only. Production never falls back to local disk. Database initialization stays lazy so website builds and public marketing pages do not require live database access.
- Store leads, vehicles, bookings, incoming messages, Google events, month caches, send attempts and integration metadata as separate bounded documents, not one growing JSON document. Preserve current revisions and validation. Use Firestore transactions with a shared workspace revision/lock to serialize updates across server instances, including competing bookings and duplicate registrations. Transactions contain database operations only: never send mail, call Google, or create sessions inside a retried callback.
- Keep shared Google mailbox connection separate from personal staff login. Only configured integration administrators may connect/disconnect or replace the shared account; any signed-in user can use the existing explicit inbox and calendar actions. Administrator emails come from a server-only configuration value; no automatic first-user administrator. Continue requiring a verified everydaystravel.co.uk account for the shared business mailbox connection.
- Encrypt shared Google access/refresh tokens with AES-256-GCM using a stable server environment key, and store ciphertext only in a server-only integration document. Bind OAuth state/PKCE to the initiating staff session and canonical redirect. Serialize token refresh with database coordination or tolerate safe refresh-token-preserving compare-and-set; do not overwrite newer credentials after reconnect/disconnect.
- Move Calendar exports/follow-ups outside transaction callbacks. Stable external IDs, reservation revision checks, and operation claims prevent stale concurrent exports; pending/ambiguous attempts remain visible and must not be blindly resent. Existing mail-send idempotency remains durable across instances.
- Add a minimal login screen in the existing light shadcn style and a sign-out action. Keep the logo/navigation sidebar free of profile/footer clutter. API authorization failures route users back to sign-in without showing private cached data. Poll/refetch on focus at a modest interval for shared updates; revisions prevent lost edits.
- Record the actor UID/email and server timestamp for writes in server-only audit records. Do not log message bodies or credentials. Configure appropriate cache lifetimes and bounded cache eviction; avoid unbounded email and event documents. Retention follows the prior 24-month enquiry design, with explicit deletion guidance for other records, encrypted backups and deployment documentation.

## Local data migration
Provide an explicit authenticated administrator-only import mechanism or local migration script. Validate records, refuse overwrite of a populated shared workspace by default, make import idempotent, and preserve revisions/source IDs and booking conflicts. Do not upload local emails or tokens simply by deploying code. Shared Google account reconnect is preferred to copying the Mac encryption key.

## Scope boundaries
Public website forms and delivery continue operating unchanged in this task. Automatic web-lead capture/attribution from the earlier core-engine design is a separate task. No WhatsApp, Instagram or Analytics integration is added. Do not change privacy-policy prose without clearly identifying the substantive new wording. No browser interaction: user expressly prohibited opening/checking the browser.

## Deployment and external prerequisites
No Firebase configuration or credentials are currently present; no Firebase/Vercel management connector or CLI session is available in this workspace. Implementation and automated tests can be completed locally. Activation requires an owner-accessible Firebase project, Google auth provider, London Firestore, deny-client rules, session and encryption settings, integration administrator email configuration, hosting environment values, authorised everydaystravel.co.uk domain and the production Google integration callback URI. Do not claim live readiness until a deployed sign-in/shared-data check has succeeded. The connected business Google project previously had Gmail/Calendar APIs disabled; this is a separate activation check.

Run full suite, TypeScript, scoped lint and production build. Independent review required before release. Push/deploy once implementation is validated and required external setup is complete; report any unavailable setup honestly.
